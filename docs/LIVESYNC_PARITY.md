# LiveSync settings parity: implementation plan

---

## 1. HONEST SCOREBOARD

137 unique plugin settings audited (the input array has 138 entries; `syncMaxSizeInMB` appears twice).

**By reachability**

| Reachability | Count | Meaning |
|---|---:|---|
| `engine-option` | 19 | A field on `DirectFileManipulatorOptions`. Directly settable by us. |
| `peer-layer` | 24 | The engine ignores it; our peer code would have to implement the behaviour. |
| `obsidian-only` | 64 | Needs an Obsidian API, UI surface, or namespace our vault layer refuses. |
| `dead` | 30 | No runtime code reads it at the pinned commit, or the engine hardcodes it. |

**By our status**

| Status | Count |
|---|---:|
| `absent` | 100 |
| `hardcoded-default` | 19 |
| `auto-adopted-from-remote` | 13 |
| `exposed` | 5 |

**The honest number.** 43 settings (19 engine-option + 24 peer-layer) are genuinely applicable to a server-side port. Of those 43:

- **5 are operator-settable today** (`couchDB_URI`, `_USER`, `_PASSWORD`, `_DBNAME`, `passphrase`).
- **13 are settable only by the remote**, via `mergeRemoteTweaks()`. The operator has no say, and on a database with no milestone document there is no remote value either, so these silently fall to engine defaults.
- **7 are frozen at a value nobody chose**, either by an omission in `buildCouchConf()` (`enableCompression`) or by the engine's own `get settings()` getter.
- **18 are simply not implemented.**

So: **5 of 43, or 12%.** Our 9-field block looks larger than it is because 3 of the 9 (`liveMode`, `intervalSec`, `includeInternal`) are WebObsidian concepts, not plugin fields, and 1 (`obfuscatePassphrase`) bundles two plugin fields into one.

**The one thing that makes this worse than 12% sounds.** We never write the milestone document (`peer-couchdb.ts:559`, `if (!milestone)` attaches the feed and moves on). So if we seed a fresh database, we write chunks under engine defaults, and the first Obsidian client to connect writes the milestone from *its* settings. On our next connect we adopt those and every document we already wrote may be unreadable. Auto-adoption is not a substitute for exposing these; it is a race we currently lose in one specific, plausible order.

## 2. TIER 1: ship now

**P0 prerequisite, do this first (30 minutes).** `server/vendor/livesync-engine/index.d.ts` is hand-maintained and has drifted from upstream at exactly the types Tier 1 touches:

| index.d.ts line | Declares | Upstream `common/types.ts` |
|---|---|---|
| 152 | `E2EEAlgorithm = "" \| "v2" \| "v3"` | `"" \| "v2" \| "forceV1"` |
| 153 | `ChunkSplitterVersion = number` | `"" \| "v1" \| "v2" \| "v2-segmenter" \| "v3-rabin-karp"` |

`"v3"` is not a value the engine accepts, and `number` would let any chunk-splitter value through typecheck. `peer-couchdb.ts` imports both types for its `RemoteTweaks` interface, so this is already wrong in shipped code. Fix `index.d.ts` (it is ours, `upstream/` is not touched). Without this, the `E2EEAlgorithm` field below cannot be typed correctly.

### The tri-state pattern (shared by T1.1 to T1.4)

All four of these are in `mergeRemoteTweaks()`'s adopt-or-die path. Exposing them as plain booleans would destroy adoption: an operator who never touched the field would be asserting `false` against a remote that says `true`. Model them as three-valued.

Add to `server/src/services/settings.ts`, immediately above `LiveSyncBlockSchema`:

```ts
/**
 * A wire-format setting the remote also has an opinion about.
 *
 * 'auto' means "whatever the remote's milestone document says", which is how a
 * peer joins an existing cluster without the operator transcribing anything.
 * 'on'/'off' PIN the value: mergeRemoteTweaks() then refuses to adopt over it
 * and treats a remote disagreement as fatal instead of silently switching.
 *
 * Pinning matters in exactly one case that 'auto' cannot cover, and it is not
 * hypothetical: this peer never WRITES the milestone document (see the
 * `if (!milestone)` branch in peer-couchdb.ts). Seed a fresh database from
 * WebObsidian and the first Obsidian client to connect writes the milestone from
 * ITS settings; on our next connect we adopt those, and everything we already
 * wrote under the engine defaults becomes unreadable or is silently re-uploaded
 * as a second set of documents. Pinning is how an operator seeding a new
 * database says what the wire format is before anyone else gets a vote.
 */
function triStateTweak(field: string) {
  return z
    .enum(['auto', 'on', 'off'])
    .default('auto')
    .catch((ctx: { input: unknown }) => {
      console.warn(
        `[settings] refusing livesync.${field} ${JSON.stringify(ctx.input)}; adopting the remote's value instead`,
      );
      return 'auto' as const;
    });
}
```

### T1.1 `handleFilenameCaseSensitive` — highest silent-corruption risk

**Zod line** (in `LiveSyncBlockSchema`):

```ts
  /**
   * Whether filenames are hashed to document ids case-sensitively.
   *
   * Upstream lists this in IncompatibleChanges for a reason: `$$path2id` passes
   * `!this.options.handleFilenameCaseSensitive` as the `caseInsensitive` flag to
   * `path2id_base`, so a mismatch hashes `Notes/Foo.md` to a DIFFERENT document
   * id on each side. Nothing errors. The two clients simply stop seeing each
   * other's edits to that file and the vault grows a duplicate document per note.
   * There is no repair after the fact that does not involve reading both copies.
   */
  handleFilenameCaseSensitive: triStateTweak('handleFilenameCaseSensitive'),
```

**Plumbing**

1. `server/src/services/settings.ts` : the field above.
2. `server/src/routes/settings.ts` : in `sanitizeLiveSync()`, add
   ```ts
   if (v.handleFilenameCaseSensitive !== undefined) {
     fields.handleFilenameCaseSensitive = requireTriState(
       v.handleFilenameCaseSensitive, 'livesync.handleFilenameCaseSensitive');
   }
   ```
   plus one shared helper `requireTriState(value, field)` that throws `httpError(400, ...)` for anything not in `['auto','on','off']`.
3. `server/src/services/livesync.ts` `buildCouchConf()` : `handleFilenameCaseSensitive: triToBool(s.livesync.handleFilenameCaseSensitive)` where `triToBool` returns `undefined` for `'auto'`.
4. `server/src/services/livesync.ts` `configSignature()` : **add it to the hashed material array.** Miss this and a save appears to work, the running pair keeps the old value, and the setting only takes effect on the next process restart. That is the same silent-failure shape the file's own comment warns about.
5. `server/src/services/livesync/types.ts` : add `pinnedTweaks?: readonly string[]` to `LiveSyncCouchDBConf`; `buildCouchConf()` populates it with every field the operator did not leave on `'auto'`.
6. `server/src/services/livesync/peer-couchdb.ts` `mergeRemoteTweaks()` : in the adoption loop, `if (conf.pinnedTweaks?.includes(key)) { if (current !== value) throw new LiveSyncFatalError(...); continue; }`.
7. `redactSettings()` : **no change needed.** It spreads `...s.livesync`, so non-secret fields flow out automatically. Confirm, do not edit.

**What breaks if it is wrong.** Pinned `'on'` against a case-insensitive cluster means every document id differs from every other peer's. The vault appears to sync (no errors, documents are written) and diverges completely. This is why a pinned mismatch must be `LiveSyncFatalError`, never a warning.

### T1.2 `E2EEAlgorithm` — undecryptable content

```ts
  /**
   * The end-to-end encryption algorithm, when a passphrase is set.
   *
   * The engine's DirectFileManipulator path defaults to V2 (AES-256-GCM with
   * HKDF) while the plugin's own DEFAULT_SETTINGS is V1 (legacy). So the two
   * disagree by default, and the disagreement is only reconciled if the remote's
   * milestone document happens to carry an `E2EEAlgorithm` key. An older plugin
   * that does not write it leaves us writing V2 into a V1 cluster: every
   * document we push is undecryptable there, and every document they push is
   * undecryptable here, with no error on either side.
   */
  e2eeAlgorithm: z
    .enum(['auto', 'v1', 'v2'])
    .default('auto')
    .catch((ctx: { input: unknown }) => {
      console.warn(
        `[settings] refusing livesync.e2eeAlgorithm ${JSON.stringify(ctx.input)}; adopting the remote's value instead`,
      );
      return 'auto' as const;
    }),
```

**Plumbing.** Same seven steps. `buildCouchConf()` maps `'v1' -> ''`, `'v2' -> 'v2'`, `'auto' -> undefined`. Note the engine's wire value for V1 is the empty string, not the literal `'v1'`; the settings-facing name is friendlier and the mapping is one line.

**What breaks if it is wrong.** Content written under the wrong algorithm cannot be decrypted by anyone, including us after a restart. Unrecoverable without the original plaintext.

### T1.4 `enableCompression` — currently a hard connect blocker

Today `buildCouchConf()` omits the field entirely, so it is permanently `undefined`, and `mergeRemoteTweaks()` line 1035 throws `LiveSyncFatalError` on any mismatch. **We cannot connect to any compression-enabled database at all, and there is no setting that fixes it.**

```ts
  /**
   * Chunk compression. Currently unreachable: buildCouchConf() omits the field,
   * so it is permanently off, and mergeRemoteTweaks() throws a fatal error on
   * any mismatch. A CouchDB database with compression enabled is therefore
   * un-joinable by this build, with no operator-visible remedy.
   *
   * 'auto' relaxes that: compression is a negotiated wire format, so adopting
   * the remote's value is what the plugin itself does. 'on'/'off' keep the fatal
   * check, for an operator seeding a new database who wants to decide.
   */
  enableCompression: triStateTweak('enableCompression'),
```

**Plumbing.** Steps 1 to 7 as above, **plus** one change specific to this field: `mergeRemoteTweaks()`'s existing unconditional throw at line 1035 must become conditional on `enableCompression` being pinned. On `'auto'`, move it into the adoption literal alongside `hashAlg` and friends. Keep `encrypt` and `usePathObfuscation` fatal exactly as they are; those two are checked against local *presence* of a passphrase, not against a value, and adopting them is never right.

**What breaks if it is wrong.** Wrong value with a pin: every chunk we write is unreadable by other clients and vice versa. Left as today: a whole class of deployment cannot use this backend and the error message does not name a setting they can change.

### T1.5 `syncMaxSizeInMB` — files silently skipped by every other peer

We have no size gate anywhere. `StoragePeer.processPath()` reads and pushes whatever it finds.

```ts
  /**
   * Refuse to push a vault file larger than this, in megabytes. 0 means no limit.
   *
   * The Obsidian plugin checks its own `syncMaxSizeInMB` (default 50) BEFORE
   * calling putDBEntry, and refuses to pull anything above it. We have no such
   * gate, so a large file is pushed to CouchDB, consumes storage there, and is
   * then refused by every Obsidian client in the cluster. The document is
   * orphaned: present in the database, on nobody's disk, and reported by nothing.
   *
   * Default 0 rather than 50 on purpose. Defaulting to a limit would silently
   * START skipping files on an existing install after an upgrade, which is the
   * same invisible-divergence failure in the opposite direction. The storage
   * peer instead logs a notice for every push above 50 MB naming this setting,
   * so the operator learns about it from the thing that is actually happening.
   */
  maxFileSizeMB: z
    .number()
    .int()
    .min(0)
    .max(4096)
    .default(0)
    .catch((ctx: { input: unknown }) => {
      console.warn(
        `[settings] refusing livesync.maxFileSizeMB ${JSON.stringify(ctx.input)}; pushing files of any size instead`,
      );
      return 0;
    }),
```

**Plumbing**

1. `server/src/services/settings.ts` : the field.
2. `server/src/routes/settings.ts` `sanitizeLiveSync()` : integer, `>= 0`, `<= 4096`, else 400. Same shape as the existing `intervalSec` check.
3. `server/src/services/livesync/types.ts` : add `maxFileSizeMB?: number` and `warnFileSizeMB?: number` to `LiveSyncStorageConf`.
4. `server/src/services/livesync.ts` `buildStorageConf()` : currently takes no arguments. Change to `buildStorageConf(s: Settings)` and pass it at the one call site (`livesync.ts:480`).
5. `server/src/services/livesync/peer-storage.ts` `readFile()` : after the `stat`, before reading content, `if (limit > 0 && st.size > limit) { log(...,'notice'); return { kind: 'skip' }; }`. Put it in `readFile()`, not `processPath()`, so the offline scan and the watcher path share one gate. Emit the advisory notice at 50 MB regardless of the limit.
6. **Do not** add this to `configSignature()`. It is not a wire-format field and changing it must not tear down the connection. It is read per-file from `conf`, so a settings change needs the storage conf refreshed; simplest correct approach is to read it through a getter on the runtime rather than a captured number.

**What breaks if it is wrong.** Set too low and files stop replicating with only a log line to say so. This is the one Tier 1 setting where a wrong value causes the exact problem it exists to prevent, so the notice log is not optional.

### T1.6 Database name suffix — a documentation fix, not a field

`additionalSuffixOfDatabaseName` is reachability `obsidian-only` (no engine code reads it), but its interop risk is real: the plugin concatenates it onto `couchDB_DBNAME` in its own code, so the actual CouchDB database is `name + suffix`. An operator who copies only the `couchDB_DBNAME` field from their plugin settings points us at a database that does not exist or is empty. CouchDB answers cleanly, our probe succeeds if the database exists, and nothing ever syncs.

**Cost: two strings, no schema change.** Our `database` field already IS the final name.

- `web/src/components/Settings.tsx`, the `Database` row `desc`: append `If the Obsidian plugin has a "Database suffix" set, include it here: the plugin joins the two, so the real database name is name + suffix.`
- `server/src/services/settings.ts`, the `database` field comment: same note, one sentence.

Ship this in the Tier 1 change. It is the cheapest interop fix in the whole audit.

## 3. TIER 2: ship next

Ordered by consequence.

### T2.1 `trashInsteadDelete` — local data loss on an errant remote delete

`StoragePeer.delete()` calls `fs.rm(abs, { force: true })`. Permanent. The plugin's default is the trash bin. A remote delete that arrives by mistake (a conflict resolved the wrong way, a client with a stale checkpoint) destroys the local copy with no undo.

This is not Tier 1 only because the content is still in CouchDB's revision history, and because the existing code has a documented reason to avoid `vault.ts`'s `trash()`: the trash root is operator-configurable and `index.ts`'s watcher only ignores the literal `.trash`, so with any other root the "deleted" file reappears at a watched path and is pushed straight back out. That is a deletion loop, which is worse.

**The fix is a LiveSync-owned trash directory, not the vault trash.** Write to `data/livesync-trash/<timestamp>/<relpath>` (outside the vault root, therefore outside the watcher, therefore no loop).

```ts
  /**
   * Move remotely-deleted files into data/livesync-trash instead of unlinking.
   *
   * Deliberately NOT vault.ts's trash(): its root is operator-configurable and
   * index.ts's watcher only ignores the literal name `.trash`, so with any other
   * root the deleted content reappears at a watched path, is observed as a new
   * file, and is pushed back to CouchDB, where every peer materialises it. A
   * deletion loop. The LiveSync trash lives under data/, outside the vault root,
   * so no watcher can see it.
   */
  trashRemoteDeletes: z.boolean().default(true).catch(true),
  /** Days to keep LiveSync trash before sweeping. 0 disables the sweep. */
  trashRetentionDays: z.number().int().min(0).max(365).default(30).catch(30),
```

**Plumbing.** Schema; `routes/settings.ts` boolean + int checks; `LiveSyncStorageConf` gains `trashDir?: string`; `buildStorageConf()` resolves it; `peer-storage.ts delete()` renames instead of `rm` (falling back to `rm` if the rename crosses a device boundary). Add a sweep on `start()`. Not in `configSignature()`.

**What breaks if it is wrong.** A trash directory inside the vault root is a deletion loop that propagates to every peer. Assert at construction that the resolved trash dir is not under the vault root, and refuse to start if it is.

### T2.2 `couchDB_CustomHeaders` — a class of deployment cannot connect at all

Our two HTTP paths both send bare requests: `probeCouch()` builds only `Authorization`, and the `$$createPouchDBInstance` override passes only `auth`. Any gateway requiring a header (Cloudflare Access, an API-gateway key, a tenant selector) rejects us with no setting to fix it.

```ts
  /**
   * Extra HTTP headers sent with every CouchDB request, as "Name: value" lines.
   *
   * Mirrors the plugin's couchDB_CustomHeaders, which is how a self-hosted
   * CouchDB behind an authenticating gateway is reached. Both of our HTTP paths
   * currently send none, so such an endpoint is unreachable by this build.
   *
   * Values are treated as SECRETS by redactSettings(): a gateway header is an
   * API key in practice, and shipping it to the client in a settings response is
   * the same mistake as shipping git.token would be.
   *
   * The refine is header-injection defence, not tidiness: a value containing CR
   * or LF splits one request into two at the socket, letting a settings edit
   * forge an arbitrary second HTTP request against CouchDB with our credentials
   * attached.
   */
  customHeaders: z
    .array(z.string())
    .default([])
    .transform((v) => v.map((line) => line.trim()).filter(Boolean))
    .refine((v) => v.every((line) => /^[A-Za-z0-9!#$%&'*+.^_`|~-]+:[^\r\n]*$/.test(line)), {
      message: 'each entry must be a single "Name: value" line with no CR or LF',
    })
    .catch((ctx: { input: unknown }) => {
      console.warn(
        `[settings] refusing livesync.customHeaders (${Array.isArray(ctx.input) ? ctx.input.length : 0} entries); sending no custom headers instead`,
      );
      return [] as string[];
    }),
```

Note the `console.warn` deliberately prints a count, not the value. The rejected value may be the credential.

**Plumbing**

1. Schema.
2. `redactSettings()` : **must be edited.** `customHeaders: s.livesync.customHeaders.length ? [REDACTED_SECRET] : []`. This is the one Tier 2 field that touches redaction.
3. `routes/settings.ts` : add `customHeaders` to `LiveSyncPatch['secrets']`, not `fields`, so the round-trip rule applies. An absent or sentinel value leaves the stored headers alone; `null` clears them. Reuse `readSecret()`'s shape.
4. `livesync/types.ts` : `customHeaders?: readonly string[]` on `LiveSyncCouchDBConf`.
5. `buildCouchConf()` : pass through. **Add to `configSignature()`** (a header change needs a fresh connection).
6. `peer-couchdb.ts` : parse once into a `Record<string,string>` in `buildManipulator()`; merge into `probeCouch()`'s `headers` object and into the `fetch` wrapper inside `$$createPouchDBInstance`. Both, or the probe succeeds and replication fails.

**What breaks if it is wrong.** A malformed header stops the connect. A leaked one is a credential in a settings response, which is why redaction is step 2 and not an afterthought.

### T2.3 `syncOnlyRegEx` / `syncIgnoreRegEx` — files skipped, or over-shared

`EntryManager.isTargetFile()` reads these from a settings object built by spreading `DEFAULT_SETTINGS`, and there is no `DirectFileManipulatorOptions` field to override them, so the engine always sees empty patterns. Filtering has to happen in our peers.

```ts
  /**
   * If non-empty, replicate ONLY vault paths matching this regular expression.
   * Empty means no restriction.
   *
   * Applied symmetrically in StoragePeer.readFile() and CouchDBPeer.isInterested().
   * Asymmetry here is a one-way flow: filter outbound only and remote deletions
   * of excluded files still land locally.
   *
   * A pattern that does not compile heals to "no filter" rather than to "match
   * nothing", i.e. fail open. Replicating more than intended is recoverable by
   * deleting documents; replicating less is a vault that silently stops syncing.
   */
  syncOnlyRegEx: z
    .string()
    .default('')
    .superRefine((v, ctx) => {
      if (!v) return;
      try { new RegExp(v); } catch { ctx.addIssue({ code: 'custom', message: 'must be a valid regular expression' }); }
    })
    .catch((ctx: { input: unknown }) => {
      console.warn(
        `[settings] refusing livesync.syncOnlyRegEx ${JSON.stringify(ctx.input)}; replicating everything instead`,
      );
      return '';
    }),
  /** Same treatment, inverted: skip vault paths matching this. Ignore wins over only. */
  syncIgnoreRegEx: z
    .string()
    .default('')
    .superRefine(/* identical */)
    .catch(/* identical, message says "ignoring nothing instead" */),
```

**Plumbing.** Schema; `routes/settings.ts` compiles the pattern and 400s on failure (do not defer to the schema's fail-open); a shared `compilePathFilter(only, ignore)` helper in `livesync/types.ts` returning a single predicate; wire it into `peer-storage.ts readFile()` (after `isIgnoredVaultPath`) and `peer-couchdb.ts isInterested()` (after the `':'` check). **Not** in `configSignature()`, but a change must trigger a rescan or newly-included files stay invisible until they are next edited.

**What breaks if it is wrong.** A too-narrow `syncOnlyRegEx` stops replication silently. Both peers must be given the same predicate object, not two independently compiled ones.

### T2.4 `useIgnoreFiles` + `ignoreFiles` — expose together or not at all

`.gitignore`-style exclusion. `ignoreFiles` alone does nothing; `useIgnoreFiles` alone has no file list. One change, two fields:

  useIgnoreFiles: z.boolean().default(false).catch(false),

    .transform((v) => v.map((s) => s.trim()).filter(Boolean))

Plumbed into the same `compilePathFilter` seam as T2.3. The engine exports `isAcceptedAll()` from `string_and_binary/path.ts` but it takes the parsed list as a parameter, so we own the parsing and the file watching. Lowest value-per-line item in Tier 2; do it last.

### T2.5 On-demand chunk pacing: `concurrencyOfReadChunksOnline`, `minimumIntervalOfReadChunksOnline`

```ts
  chunkFetchConcurrency: z.number().int().min(1).max(200).default(40).catch(40),
  chunkFetchIntervalMs: z.number().int().min(0).max(10_000).default(50).catch(50),
```

**Blocked on verification.** Both audit entries carry `unsure: true` because `LiveSyncManagers`'s constructor may throw `No NetworkManager available` before `ChunkFetcher` is ever built. Our vendor package ships `shim.js` for exactly this (the `navigator` shim, per the `sideEffectsNote` in the vendor package.json), so it probably does initialise, but "probably" is not a basis for shipping a setting.

**Do this before writing the schema line:** run the backend against a real CouchDB with `LIVESYNC_DEBUG=1`, confirm `ChunkFetcher` exists on `man.managers`, and confirm the value it read. If it does not initialise, these two fields are `not-applicable`, not `expose-later`, and the audit should be corrected.

There is no `DirectFileManipulatorOptions` field for either, so plumbing means reaching into `man.managers` after construction. That is engine-internal, which `peer-couchdb.ts` already refuses to do elsewhere on principle (see the `buildManipulator()` comment about `liveSyncLocalDB`). Weigh that before committing.

### T2.6 `syncMinimumInterval` / debounce

Trivial, low risk, useful on high-churn vaults. `debounceMs` is hardcoded to 300 in `buildStorageConf()`.

```ts
  /**
   * Trailing debounce per path before a local change is read and pushed, in ms.
   * The default matches index.ts's watcher awaitWriteFinish.stabilityThreshold,
   * so an editor's write-truncate-write collapses into one push. Raising it
   * trades push latency for fewer CouchDB writes on a bursty vault.
   */
  debounceMs: z.number().int().min(0).max(60_000).default(300).catch(300),
```

`buildStorageConf(s)` already needs a `Settings` argument for T1.5; take this along with it.

### T2.7 JWT authentication (6 fields, one unit)

`useJWT`, `jwtAlgorithm`, `jwtKey`, `jwtKid`, `jwtSub`, `jwtExpDuration`. Standard HTTP auth, implementable entirely in our peer layer with `node:crypto` WebCrypto, no engine involvement. The largest single Tier 2 item because it needs a sign-and-rotate cycle, not just a setting.

`jwtKey` is key material: it goes in `LiveSyncPatch['secrets']` and in `redactSettings()`. `jwtAlgorithm` is `z.enum(['HS256','HS512','ES256','ES512'])`. Injected in the same two places as T2.2's headers (`probeCouch` and the fetch wrapper), with re-signing on `jwtExpDuration/2`.

Ship this only if a real deployment needs it. Basic auth covers self-hosted CouchDB, which is the stated target.

### T2.8 Chunking tuning, for seeding a new database

`minimumChunkSize`, `customChunkSize`, `chunkSplitterVersion`, `hashAlg`, `enableChunkSplitterV2`, `useEden` + `maxChunksInEden` + `maxTotalLengthInEden` + `maxAgeInEden`, `doNotUseFixedRevisionForChunks`.

All 10 are auto-adopted today and a mismatch costs deduplication, storage and bandwidth, never correctness. They matter in exactly one scenario: seeding a brand-new database where no milestone exists to adopt from.

Model them all with the same tri-state / `'auto'` idiom (numeric ones as `z.union([z.literal('auto'), z.number().int()...])`), reuse the `pinnedTweaks` mechanism from Tier 1, and put them behind an "Advanced" disclosure. One change, ten fields, no new mechanism.

### T2.9 `batchSave` / `batchSaveMinimumDelay` / `batchSaveMaximumDelay`

Coalescing multiple rapid saves into one push. Our per-path `debounceMs` (T2.6) covers most of the benefit and there is no batch-max-delay concept. Implement only if T2.6 proves insufficient in practice. No wire impact.

### T2.10 `deleteMetadataOfDeletedFiles`

`DirectFileManipulatorV2`'s `get settings()` hardcodes it to `DEFAULT_SETTINGS` (false) at line 248 regardless of options, so the engine always soft-deletes. Exposing it requires bypassing the engine's managed delete path entirely. **Do not do this.** Soft-delete is also the safer default. Record it as a known, deliberate divergence.

## 7. RISKS

Everything here is about Tier 1 colliding with `mergeRemoteTweaks()` in `peer-couchdb.ts`.

### R1. Auto-adoption silently overwrites operator intent

`mergeRemoteTweaks()` line 1079-1085 unconditionally assigns every non-`undefined` remote value over the local config for 13 fields. Four of those become operator-settable in Tier 1. Without a change, an operator sets `handleFilenameCaseSensitive: 'on'`, the remote says off, we adopt off, and the UI keeps displaying "on". The setting is a lie.

**Resolution.** The `pinnedTweaks` mechanism, specified in T1.1 step 5-6. `'auto'` omits the key from `pinnedTweaks` and adoption proceeds exactly as today. A pinned key is never adopted, and a remote disagreement throws `LiveSyncFatalError` with a message naming the setting, the local value and the remote value. Not a warning: an unnoticed mismatch on any of these four costs the vault.

### R2. `configSignature()` omission makes new settings inert until restart

`configSignature()` (livesync.ts:320) hashes 9 fields. `ensureRunning()` compares the hash and, on a match, updates only `liveMode` and returns the existing pair. Add a Tier 1 field without adding it to the signature and a save reports success, the UI shows the new value, and the running peer keeps the old one. The operator only finds out after a restart, possibly weeks later, possibly after the wrong wire format has been written to thousands of documents.

**Resolution.** Add all four Tier 1 tweak fields and `customHeaders` to the material array. Do **not** add `maxFileSizeMB`, `debounceMs`, the regex filters, or the trash settings: none require a new connection, and tearing the pair down on a filter change costs a full rescan for nothing.

**Verification, per field:** save a change, then read `GET /api/livesync/status` and confirm the peer reconnected (the log emits `configuration changed; restarting the peer pair.`). A field that should restart and does not is the failure this risk describes.

### R3. Seeding a fresh database is the case adoption cannot cover, and we currently lose it

We read the milestone document and never write one (`peer-couchdb.ts:559`). Sequence:

1. WebObsidian connects to an empty database. No milestone, so no adoption. The engine's defaults apply: E2EE **V2**, `handleFilenameCaseSensitive` **false**, compression **off**.
2. We push the whole vault under those defaults.
3. An Obsidian client connects. The plugin's `DEFAULT_SETTINGS` has `E2EEAlgorithm` **V1**. It writes the milestone from its own settings.
4. We reconnect and adopt V1.
5. Everything from step 2 was written with V2. It is now undecryptable, by us and by them.

**Resolution, in order of preference:**

- **(a)** When `connectAndWatch()` finds no milestone **and** any of the four Tier 1 tweaks is on `'auto'`, log a `notice` naming each value we are about to write and stating that the first Obsidian client to connect will overwrite it. Cheap, honest, ships with Tier 1.
- **(b)** In the UI, when the status reports `remote-created` as absent (the no-milestone marker the peer already records), show a banner: "This database has never been initialised by a LiveSync client. Pin the encryption algorithm and case sensitivity to match your Obsidian clients before syncing."
- **(c)** Write the milestone ourselves from our config. This is the correct fix and it is **out of scope for Tier 1**: `MILESTONE_DOCID` is already hardcoded here, but the document has a schema we would be guessing at, and writing a wrong milestone poisons the whole cluster rather than just this peer. Do (a) and (b) now; evaluate (c) with a real database in front of you.

### R4. Relaxing the compression check changes an existing safety behaviour

Today a compression mismatch is always fatal. On `'auto'` it becomes an adoption. That is correct (compression is a negotiated wire format and the plugin adopts it too) but it is a behaviour change on an existing safety check, so it needs to be deliberate and reviewed as such rather than arriving as a side effect of adding a field.

Leave the `encrypt` and `usePathObfuscation` throws at lines 1020-1031 exactly as they are. Those two check for the local *presence* of a passphrase, not for a value match, and there is nothing to adopt.

### R5. The engine sees the merged config; `configSignature()` sees the settings

`this.conf = merged` (peer-couchdb.ts:537) mutates the peer's config after adoption, while `configSignature()` is computed from `buildCouchConf(s)`, pre-merge. They do not drift today because the signature answers "did the operator change something", not "what is the peer using". Keep it that way. Deriving the signature from the post-merge config would make every adoption look like an operator change and restart the pair in a loop.

### R6. `maxFileSizeMB` is the one Tier 1 field whose wrong value causes the problem it prevents

Set it to 1 and most of the vault stops replicating, with only a `notice` log line to explain. Mitigations, all in T1.5: default 0 (no limit, today's behaviour, no surprise on upgrade); a `notice` per skipped file naming the path and the setting; the UI help text stating the plugin's default is 50 and that files above a peer's limit are never pulled by that peer. Do not "helpfully" default this to 50.

### R7. T2.5 rests on an unverified assumption

Two audit entries carry `unsure: true` on the same question: whether `LiveSyncManagers` initialises at all in our Node process, or throws `No NetworkManager available`. If it throws, `ChunkFetcher` never exists and those two settings are not `expose-later`, they are `not-applicable`. Verify against a live CouchDB before writing either schema line. Reaching into `man.managers` to plumb them also violates the no-engine-internals rule that `buildManipulator()`'s comment states explicitly; weigh that against the benefit, which is only visible on a rate-limited gateway.

## MIT licence compliance analysis

MIT requires: "The above copyright notice and this permission notice shall be included in all copies or substantial portions of the Software."

For the vendored livesync-commonlib code specifically:

- `server/vendor/livesync-engine/LICENSE` contains the full text with the correct copyright line. That file is listed in the vendor package's `"files"` array, so it is preserved in any copy of the package.
- `bundle/engine.js` (the compiled artifact that actually ships into `server/dist` and the desktop bundle) carries the four-line banner including the copyright line. This is inside the compiled output.
- The upstream source files under `server/vendor/livesync-engine/upstream/src/` are an unmodified copy and do not themselves carry individual copyright headers (that is upstream's own practice), so the single LICENSE file covering the whole tree is the correct approach.

Conclusion on livesync-commonlib: the MIT notice requirement is satisfied for the vendored code, provided the LICENSE file is actually distributed alongside the bundle. The `"files"` array in the vendor package.json includes `LICENSE`, which means `npm pack` would include it, but the Dockerfile copies `server/dist` and runs `npm install --omit=dev` from the workspace root, not from the vendor subdirectory. Whether the LICENSE file ends up inside the Docker image depends on how that install resolves the `file:vendor/livesync-engine` dependency: if npm copies the package contents into `node_modules/livesync-engine`, the `LICENSE` will be there. That path should be verified but is architecturally plausible.

For livesync-bridge (the reference daemon): it is used only as a design reference; no code from it is distributed. Its MIT licence text is therefore not required to appear. The code comments in the server source cite it as a reference, which is good practice but not a legal requirement.

For obsidian-livesync (the plugin): it is not vendored and no code from it is distributed. No licence reproduction is required. Attribution in user-facing documentation is conventional but not mandated by MIT.
